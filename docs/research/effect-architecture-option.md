# Option C: React SPA with an Effect API and worker

Research snapshot: October 9, 2026. The owner subsequently selected this option on October 10; [ADR 0004](../adr/0004-effect-api-and-worker.md) supersedes ADR 0001. The research below predates initialization and is a static failure review, not measured load-test evidence.

## Concrete composition

React, Vite and TanStack Router render the authenticated application. A separate Node API uses Effect HTTP API contracts and handlers. A separately runnable Node worker uses Effect for execution. PostgreSQL remains authoritative; Drizzle owns application migrations and persistence, pgvector supports future retrieval, and pg-boss supplies future durable job delivery. Private originals remain outside the database. Better Auth and AI SDK initialization stay in their dedicated issues.

Effect owns each backend process's service graph, scoped resource acquisition, cancellation and finalization. Do not add Nest's dependency-injection container to this option. Drizzle, pg-boss and external SDKs remain narrow Promise adapters; wrapping them does not remove their transaction or cancellation constraints. Browser components can use ordinary React; Effect in the backend does not require adopting Effect's frontend state system.

Effect is a library and execution model atop TypeScript. Its success/error/service type channels expose expected failures and dependencies. It does not replace the TypeScript compiler, runtime input validation, ownership checks or durable storage. [Effect type](https://github.com/effect-ts/website/blob/main/apps/web/src/content/docs/v4/getting-started/the-effect-type.mdx), [Layers](https://github.com/effect-ts/website/blob/main/apps/web/src/content/docs/v4/requirements-management/layers.mdx), [scoped resources](https://github.com/effect-ts/website/blob/main/apps/web/src/content/docs/v4/resource-management/scope.mdx).

T3 Code's EffectWorker is wired inside its Node server runtime. It is not evidence of a separately deployed OS-process worker. Option C deliberately proposes that additional process boundary for Sprout's media/provider workload.

What Sprout can borrow: one typed backend service graph, schema-backed transport boundaries, scoped resources and explicit durable command identities. What it should not inherit automatically: Electron, SQLite, provider orchestration/event sourcing, WebSocket RPC for every operation, its patches, or its frontend state machinery. A conventional HTTP API plus streaming where required remains a valid Effect design.

## Static failure stress review

These are design obligations and predicted failure modes, not observed test results.

| Scenario                                         | What option C helps with                                  | Remaining obligation / anomaly                                                                                                                                                                                                                 |
| ------------------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Process dies between receipt and enqueue         | Typed service boundaries can expose the operation clearly | Receipt and job must commit on the same PostgreSQL transaction connection; two wrapped Promises are still two non-atomic operations. Verify pg-boss/Drizzle transaction integration in its feature issue.                                      |
| File retained, database commit fails             | Scoped cleanup helps cooperative failure                  | A hard kill skips finalizers. Staging manifests and restart reconciliation remain necessary; database and filesystem are not one transaction.                                                                                                  |
| Provider succeeds, completion recording fails    | Explicit typed failures expose the failed stage           | Retry can repeat paid work. Persist attempt identity and outcomes; use provider idempotency where actually supported, reconcile uncertainty, and never claim exactly-once external execution.                                                  |
| Compose Watch restarts worker                    | Process scope gives one finalization owner                | Mark unready, stop taking work, drain within a bounded grace period, then cancel; durable claims need recovery after forced termination. Issue #2 proves shutdown/readiness only, not job recovery.                                            |
| Browser disconnects during streaming             | Scoped request work can be interrupted                    | Adapter must pass AbortSignal and underlying API must honor it. Cancellation cannot undo committed writes or a completed provider call. Durable background work must not accidentally belong to the browser request scope.                     |
| Owner corrects or Trashes item during processing | Error and dependency types aid contract clarity           | Publication must recheck owner, revision and lifecycle in a short transaction. An Effect service requirement is not authorization.                                                                                                             |
| PostgreSQL disappears after startup              | Readiness can run bounded dependency checks               | A Layer having initialized once does not prove continued connectivity. Liveness stays separate from readiness; API and worker become unready for required DB failures.                                                                         |
| Database is saturated                            | Bounded concurrency and cancellation help contain work    | Define separate API/worker pool budgets and admission limits. Do not retry indefinitely, allow unbounded fibers, or let health probes amplify overload. No performance advantage is asserted.                                                  |
| Auth cookie expires during a stream              | Typed middleware can supply verified user context         | Authentication, CSRF/origin rules, private-file authorization and session-expiry behavior still require explicit policy. SPA/API dev origins add proxy/cookie configuration work. Keep the eventual production API same-origin when practical. |
| Bad client consumes an unbounded stream          | Effect supplies streaming composition                     | Bound buffering and payloads; decide replay cursors and reconnect behavior. Do not introduce RPC merely for type sharing.                                                                                                                      |

The resource and interruption mechanisms are documented by Effect, but the application guarantees in the last column are Sprout design requirements. [Resource scopes](https://github.com/effect-ts/website/blob/main/apps/web/src/content/docs/v4/resource-management/scope.mdx), [creating effects and Promise adapters](https://github.com/effect-ts/website/blob/main/apps/web/src/content/docs/v4/getting-started/creating-effects.mdx), [HTTP builder example](https://github.com/effect-ts/website/blob/main/apps/web/src/features/search/server.ts).

## Readiness and issue #2 boundary

API readiness should declare PostgreSQL connectivity and required migration/extension state. Worker readiness should declare PostgreSQL connectivity and successful initialization of services actually included in its process. If pg-boss is initialized in #2, its initialized state is required; if deferred, do not claim queue readiness. Provider credentials and network availability are not readiness requirements before their features exist. Storage readiness is required only for processes that currently depend on that mount.

Migrations remain a one-shot Compose prerequisite. Health checks must have bounded timeouts and useful failure reasons without secrets. A live process provides liveness evidence; completed required initialization and dependency availability establish readiness. No processing diagnostic job is required by the owner's scope.

## Recommendation and tradeoff

Option C is coherent when the team deliberately chooses Effect as the backend programming model and prefers a client-rendered application. It provides one lifecycle system for both API and worker, without Nest DI or Next server composition. It also requires an extra application process, explicit browser/API integration, runtime/schema/error conventions, adapters for selected libraries, and willingness to follow a newly stable major release.

Its strongest future justification is complicated cancellation, cleanup, bounded concurrency and stage-specific failure handling around retained media and provider work. Its weakest justification is simply “full TypeScript”: every compared Node stack can use strict TypeScript. A readiness-only foundation can validate wiring but cannot prove that those abstractions improve the actual ingestion workflow.

The accepted implementation uses Effect services for backend composition and a browser-safe public contracts package for schema-backed transport contracts. Adapter compatibility belongs to the module owning each integration and must be checked on pinned-version upgrades. Selection replaces ADR 0001's Next.js composition and increases the runtime count, while preserving ADR 0002's PostgreSQL/durable-job principles.
