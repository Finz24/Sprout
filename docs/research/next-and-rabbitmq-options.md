# Next.js with pg-boss versus React/Nest with RabbitMQ

Research snapshot: October 9, 2026. This is an architectural assessment, not an implementation or throughput result. Existing ADRs 0001/0002 approve option A; option E would replace those decisions and requires an explicit decision before scaffolding.

## Options and recommendation

- **A:** Next.js supplies UI and HTTP composition on Node; shared domain modules own authorization and writes. A separately running Node worker executes pg-boss jobs. PostgreSQL stores authoritative records, Drizzle migrations, pgvector projections and queue state. Private originals live behind a local storage contract.
- **E:** React/Vite supplies UI; a Nest HTTP API composes the same domain responsibilities. PostgreSQL/Drizzle/pgvector stores records and a transactional outbox. An outbox dispatcher publishes to RabbitMQ; separate Node or Nest consumers execute jobs. Private originals retain the same storage contract.

**Recommendation/inference:** retain A for this owner-hosted application unless explicit broker routing, independent heterogeneous consumers or operational separation from PostgreSQL is a requirement. E is viable, but adds a durable broker, dispatcher, delivery bookkeeping and another recovery boundary. Nest and RabbitMQ solve different problems: Nest is an application framework; RabbitMQ transports messages; neither replaces a separately running execution process. Next.js need not execute slow jobs in request handlers. This recommendation follows the transaction and failure analysis below, not a speed comparison.

## Verified nearby application: Karakeep

Inspected upstream source at **`75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea`** through GitHub's API. Its [web package](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/apps/web/package.json) uses Next.js, React, Better Auth and AI SDK. Its [worker entry point](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/apps/workers/index.ts) starts distinct crawler, inference, embedding, indexing, video, asset and maintenance runners. This is concrete evidence of separating a Next.js UI/HTTP application from slow background work in a relevant saved-information product.

It is **not an exact A stack**: the [DB package](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/packages/db/package.json) uses Drizzle and better-sqlite3; its [Liteque provider](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/packages/plugins/queue-liteque/src/index.ts) opens a separate `queue.db`. The [plugin loader](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/packages/shared-server/src/plugins.ts) includes Liteque and Restate queue providers and filesystem/S3 asset providers. Its [Compose file](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/docker/docker-compose.yml) includes Chrome and Meilisearch and a persistent `/data` volume. These are analogy mismatches, not recommendations to copy its dependencies.

Two useful implementation examples: [queue contracts](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/packages/shared-server/src/queues.ts) split embedding generation from index persistence, avoiding a second model call solely because indexing failed; [HTML parsing](https://github.com/karakeep-app/karakeep/blob/75aeaaa4eb71b1d3143d7bdc6b88c66fbcfb5fea/apps/workers/workers/crawler/parseSubprocess.ts) runs in a timeout-bounded separate Node process with a bounded heap. These support stage isolation and bounded resource use, not a claim that Karakeep already implements Sprout's publication/ownership guarantees.

## Verified broker application analogue: Plane

Plane's [first-party architecture guide](https://developers.plane.so/self-hosting/plane-architecture) describes a frontend, REST API, independently executing background workers pulling RabbitMQ jobs, PostgreSQL and object storage. This is a real application analogue for a separate API/broker/worker topology. It is considerably larger than the proposed Sprout runtime.

Inspected community source on the `preview` branch at **`bab49bb978ccb56af1d78dec6c6d54dfe8d03c1c`**. Its [Compose source](https://github.com/makeplane/plane/blob/bab49bb978ccb56af1d78dec6c6d54dfe8d03c1c/docker-compose.yml) declares separate web, API, worker, beat worker and migrator services; PostgreSQL, Valkey, RabbitMQ with a persistent data volume, and an upload-store service. Its [worker setup](https://github.com/makeplane/plane/blob/bab49bb978ccb56af1d78dec6c6d54dfe8d03c1c/apps/api/plane/celery.py) uses **Python Django/Celery**, not Nest or a Node consumer. This is **not an exact E implementation** and this inspection does not establish a transactional-outbox guarantee. Neither Plane's service count nor its PostgreSQL pool settings should be copied as Sprout defaults. Its presence proves a broker topology is used by a real self-hostable app; it does not prove that Sprout requires it.

## Primary queue evidence

Context7 library resolution and separate concept queries were used for pg-boss and RabbitMQ. Context7 returned secondary DeepWiki material for pg-boss; claims were checked against **pg-boss's own source**, snapshot **`9bdce7c360d33bd43ec927671851c8f9136fcec6`**, whose package version is `12.37.1`. This is an inspected upstream snapshot, not a selected Sprout version.

pg-boss [ORM adapters](https://github.com/timgit/pg-boss/blob/9bdce7c360d33bd43ec927671851c8f9136fcec6/docs/api/adapters.md) accept an existing transaction via `db`/`executeSql`, including a documented Drizzle adapter: rollback removes both application writes and the job. Its [introduction](https://github.com/timgit/pg-boss/blob/9bdce7c360d33bd43ec927671851c8f9136fcec6/docs/introduction.md) explicitly describes at-least-once delivery after crashes/expiration. The [worker API](https://github.com/timgit/pg-boss/blob/9bdce7c360d33bd43ec927671851c8f9136fcec6/docs/api/workers.md) warns that transactional handlers hold a connection and transaction throughout execution; use short guarded publication transactions rather than wrapping provider calls in a transaction. Verify the selected release's adapter and completion semantics when versions are pinned.

RabbitMQ [publisher confirms and consumer acknowledgements](https://www.rabbitmq.com/docs/confirms) cover separate hops. A broker confirm does not confirm application publication. Manual acknowledgements with bounded prefetch control outstanding deliveries. The [reliability guide](https://www.rabbitmq.com/docs/reliability) requires idempotent consumers because retransmission after an uncertain confirm can duplicate a message. [Durable queues](https://www.rabbitmq.com/docs/queues), persistent messages and confirms belong together; a durable queue declaration alone is insufficient. [Quorum queues](https://www.rabbitmq.com/docs/quorum-queues) replicate across members; one broker on one Windows host is not host-failure high availability. [Resource alarms](https://www.rabbitmq.com/docs/alarms) can block publishers, so the dispatcher must handle blocked connections and bounded outstanding confirms.

Nest's [RabbitMQ transport](https://docs.nestjs.com/microservices/rabbitmq) exposes manual acknowledgements, prefetch and persistence options; its documented `noAck` default is `true`, which must be deliberately changed for durable processing. Do not copy the tutorial's transient queue configuration into Sprout.

The RabbitMQ maintainers' [Node work-queue tutorial](https://github.com/rabbitmq/rabbitmq-tutorials/blob/b72e82c252648af2fee5626d3f627fee23c54f29/javascript-nodejs/src/worker.js), snapshot **`b72e82c252648af2fee5626d3f627fee23c54f29`**, demonstrates quorum queues, prefetch 1 and manual acknowledgement. Its [producer](https://github.com/rabbitmq/rabbitmq-tutorials/blob/b72e82c252648af2fee5626d3f627fee23c54f29/javascript-nodejs/src/new_task.js) uses an ordinary channel without publisher confirms. This is a small primary protocol example, **not a production React/Vite/Nest/PostgreSQL/outbox application** and not proof of that exact stack's reliability.

## Failure analysis for Sprout

The following are proposed design obligations derived from Sprout's [architecture](../architecture.md), [ownership ADR](../adr/0003-authentication-and-private-ownership.md) and [testing boundary](../specs/sprout-testing-boundary.md); they are not already passing behavior.

| Failure or invariant | A: pg-boss | E: RabbitMQ with transactional outbox |
|---|---|---|
| Crash during receipt creation | Save item, receipt and job through the same PostgreSQL transaction connection. Commit exposes all; rollback exposes none. Retry submission identity returns the original receipt. | Save item, receipt and outbox event in one PostgreSQL transaction. Never substitute an API-side broker publish for the outbox transaction. |
| Crash between dispatch and bookkeeping | No second durable transport boundary for enqueue. Execution still retries. | Relay confirms publication before marking dispatched. Crash after broker acceptance but before marking creates duplicate delivery; stable event/attempt identity and idempotency remain required. |
| Crash after publication before queue completion/ack | Worker retry checks durable completed attempt/publication and avoids publishing twice. Claim-aware completion and a short shared transaction may close the DB publication/completion gap. | Consumer commits guarded publication/processed-event identity before ack. Redelivery observes committed identity and acknowledges without another publication. |
| Provider succeeded but result was not durably retained | Either option may repeat a paid call after uncertainty. Record attempt identity and persisted stage outputs; use provider idempotency when supported. Queue semantics cannot make external effects exactly once. | Same limitation. Outbox and broker confirms do not cover provider effects. |
| Worker stopped or provider unavailable | Capture can commit while jobs wait. Bound retries/backoff and expose failed stage through Needs your input; preserve usable originals. | Capture can commit while outbox waits, even with broker down, subject to backlog/disk admission limits. Relay and consumers reconnect; bound retry/dead-letter behavior. |
| Owner correction or Trash during execution | Read current ownership/revision/lifecycle again in a short publication transaction. Reject stale output and never resurrect Trash. Queue cancellation alone is insufficient. | Same rule; a message's old revision or user ID is not authorization. |
| Two-user isolation | Authenticate every web operation and enforce owner-scoped domain/DB operations; workers resolve authoritative owner/item relationships. Test pooled-connection reuse and spoofed job payloads. | Same checks at API and consumer boundaries; broker credentials and trusted producer access do not replace item authorization. |
| CPU-heavy extraction | Run bounded subprocesses/thread pools with memory/time/concurrency caps, separate from HTTP. A queue callback still runs in a Node process. | Same; RabbitMQ does not execute code or isolate CPU. Node/Nest consumers still need bounded execution. |
| Backlog/restart | Separate queue concurrency, provider budgets and DB pools; measure oldest-job age, attempts, storage and database maintenance. | Bound prefetch, relay batch/confirm window, retry policy and queue/outbox retention; monitor outbox age plus queue depth, unacked messages and broker disk/memory. |
| Local originals | Finish/verify staged bytes before acknowledging retention; persist manifests and reconcile interrupted staging/orphans. Database and filesystem do not share an ACID transaction. | Same, plus consumers on another host need an accessible authorized storage adapter; a local Windows path in a message does not provide remote access. |

[Node worker-thread guidance](https://nodejs.org/api/worker_threads.html) distinguishes CPU-bound JavaScript from asynchronous I/O; separate processes also provide useful failure isolation, as the Karakeep parser demonstrates. Neither a framework switch nor a broker choice establishes extraction throughput.

## Avoid two durable job systems for one pipeline

**Inference:** combining pg-boss and RabbitMQ for the same understanding jobs adds two sources of retry, completion and retention state. E should use PostgreSQL outbox records for reliable dispatch and RabbitMQ as its transport, rather than also enqueueing the same work in pg-boss. An outbox is dispatch bookkeeping, not a second independent worker queue. If distinct workloads require both, explicitly assign each workload and recovery owner before adding either integration.

## Health/readiness proposal

Keep process liveness separate from capability readiness; redact connection details and secrets. This is a proposed policy, not an upstream framework guarantee.

The detailed intake/processing dependencies below describe later feature capabilities. Issue #2 checks only dependencies actually initialized in its foundation: no queue consumption, job handlers, extractor binaries, providers, or artificial processing jobs are required. Do not report queue readiness if queue initialization is deferred.

- **A web intake ready:** validated configuration, expected DB migration/schema, database transaction access, compatible pg-boss queue schema and writable/readable private storage. Worker heartbeat is a processing status, not a prerequisite for accepting a durable save. Provider outage does not block original access.
- **A worker ready:** expected DB/job schemas, queue consumption operational, required private storage accessible and supported extractor binaries present. Report provider capability separately rather than turning a temporary provider outage into a liveness restart loop.
- **E UI ready:** static assets serve; API capability is separate. **API intake ready:** expected DB schema, functioning outbox insertion and private storage. Broker outage can be degraded while durable intake continues within configured backlog limits.
- **E dispatcher ready:** PostgreSQL outbox accessible, broker connection/channel established, required topology declared, publisher confirms usable and blocked-connection handling active. **Consumer ready:** broker subscription/manual acknowledgements, DB publication schema and private storage/extractors accessible.
- **PostgreSQL ready:** accepts authenticated queries and required extension/schema versions exist. **RabbitMQ ready:** appropriate broker/topology diagnostics; not merely an open TCP port. File-volume and worker readiness need their own observable checks.

## What remains unmeasured

For E, an outbox entry marked dispatched is not sufficient to recover from a broker restore that loses previously confirmed messages. Keep durable processing-request identity and terminal outcome in PostgreSQL, and reconcile nonterminal requests against broker/consumer state. Re-dispatch can duplicate delivery, so consumer idempotency remains required. The abstract model assumes confirmed messages remain durable and does not simulate such restore loss.

No app was built, no benchmark run and no queue reliability test executed. There is no evidence that either option reaches a particular jobs/sec, users count or file size. Measure a complete representative job mix, provider latency/rate limits, API latency while extracting, oldest-job age, worker CPU/memory, DB pool wait and queue/outbox storage. Inject crashes at each boundary in the table and verify persisted outcomes through retrieval. Shared-host resource contention can dominate either design; queue throughput alone cannot select the architecture.
