# Domain documentation

Before exploring or changing product behavior, read root CONTEXT.md, docs/product-direction.md, the relevant specification and docs/architecture.md. Read applicable docs/adr/ decisions before changing architectural boundaries.

Use docs/open-decisions.md for unresolved details. The approved application-testing boundary is docs/specs/sprout-testing-boundary.md. Detailed journey rules live in docs/workflow-data.json; action-flows.md and the connected HTML are generated from it.

CONTEXT.md is the domain glossary; keep implementation choices in architecture/ADRs. Use domain-modeling when resolving terminology or recording durable decisions. Surface conflicts with accepted decisions before changing them.

Use the glossary's vocabulary when naming domain concepts. If a referenced glossary or ADR does not exist, proceed with the available documentation; domain-modeling creates missing domain documents when terms or decisions are resolved.
